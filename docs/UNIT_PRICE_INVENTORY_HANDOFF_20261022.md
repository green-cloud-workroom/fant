# 구매 단가 관리 통합 — 재고관리 앱 전달 문서

작성일: 2026-10-22 (KST)

## 1. 사용자 결정과 이번 변경 범위

- 원료와 부자재 전체의 구매 단가 관리는 재고관리 앱으로 통합한다.
- 대상은 원료·영양제·제품 봉투뿐 아니라 아이스팩·드라이아이스·케이블타이·스티로폼 박스 등 구매 품목 전반이다. 이는 요구 범위이며, 실제 등록 품목 목록을 확인한 결과는 아니다.
- 생산관리의 기존 `설정 → 원료 단가 관리`는 현재 사용하지 않으므로 재고관리 구현을 기다리지 않고 화면을 제거한다.
- 기존 원료 단가와 적용일·변경 이력은 삭제하거나 초기화하지 않는다.
- 품목 등록·레시피·재고 수량의 기존 담당 앱은 유지한다. 단가 관리 책임만 재고관리로 통합한다.

이번 생산관리 변경은 화면·수정 모달·설정 영역의 단가 조회 연결 제거다. Firestore 데이터·규칙 변경, 이력 이동, 재고관리 기능 구현, 배포는 수행하지 않는다. 따라서 재고관리 기능이 준비될 때까지 앱에서 단가를 편집할 수 없는 공백은 사용자가 승인한 상태다.

## 2. 보존할 원본 데이터

Firebase 프로젝트: `fant-e5ae5` (양 앱 공유).

```text
meatTypes/{meatTypeId}
  priceHistory/{historyId}
```

원료 식별 기준은 `meatTypeId`다. 이름으로 새 품목을 만들거나 가격을 연결하지 않는다. 원료의 이름·분류·활성 상태는 부모 문서를 참조한다.

기존 가격 문서의 저장 구조 (`src/services/meatPrices.js`):

| 필드 | 의미 |
| --- | --- |
| `unitPrice` | 원/kg 기준 가격 (숫자) |
| `effectiveDate` | 적용일, `YYYY-MM-DD` |
| `prevUnitPrice` | 당시 저장한 이전 가격, 숫자 또는 null |
| `reason` | 변경 사유, 기존 기본값 `manual` |
| `createdAt` | Firestore 서버 Timestamp |
| `createdBy` | 기존 로그인 사용자의 이메일 또는 UID |

문서 ID, 부모 원료 ID, 모든 원본 필드와 Timestamp를 그대로 보존한다. 최신 가격 한 건만 남기는 변환은 하지 않는다. 비활성 원료의 과거 이력도 보존한다.

기존 감사 기록은 `activityLogs`의 `action: 'meatPrice'`, `subAction: 'manualEdit'`로 저장됐다. `details`에는 `meatTypeId`, `meatTypeName`, `prevUnitPrice`, `newUnitPrice`, `effectiveDate`가 들어간다. 이 로그도 유지하되, 가격의 기준 원본은 `priceHistory`다. 기존 저장은 가격 문서 추가 후 별도 로그 추가 순서여서 두 자료가 항상 일대일로 존재한다고 가정하면 안 된다.

**이번 작업은 원본을 건드리지 않는 방식의 보존이다. 운영 DB에서 건수·내용을 조회하거나 별도 백업 파일을 만들지는 않았다. 입력된 가격이 몇 건인지, 실제 문서가 이 구조와 모두 일치하는지는 미확인이다.**

## 3. 기존 가격 선택 규칙과 주의점

`pickLatestMeatPrice(history, dateStr)`의 기존 동작:

1. 적용일이 있고 기준일 이하인 이력을 후보로 선택한다.
2. 적용일 내림차순, 같은 적용일이면 등록시각 내림차순으로 선택한다.
3. 후보가 없으면 null이다. 미등록을 0원으로 표시하거나 계산하지 않는다.
4. 기존 화면은 오늘 날짜(KST)를 기준일로 전달했다. 기준일을 생략하면 미래 적용 가격도 후보가 되므로, 재고관리에서는 조회 기준일을 명시한다.

`prevUnitPrice`는 과거 저장 시점의 참고값이다. 과거 적용일로 이력을 추가하면 후속 문서의 이 필드가 재계산되지 않으므로 전체 시점별 가격을 복원하는 기준으로 쓰지 않는다.

기존 모달은 빈 숫자 입력을 `Number('')`로 바꿔 0으로 저장할 수 있었다. 신규 입력에서는 빈 값과 명시적 0원을 구분하고, 기존 0원을 임의로 결측으로 바꾸지 않는다. 잘못된 날짜·금액·등록시각은 누락 또는 확인 필요로 표시하고 원본을 보존한다. 적용일과 등록시각이 모두 같은 문서의 우선순위는 기존 코드에 명시돼 있지 않으므로 충돌 사례를 확인 후 결정한다.

## 4. 재고관리 구현 권장안

재고관리에 `구매 단가 관리` 화면을 만들고 다음 기존 목록을 참조한다.

| 품목군 | 기존 목록 |
| --- | --- |
| 원료 | 생산관리 소유 `meatTypes` |
| 제품 봉투 | 생산관리 소유 `bagTypes` |
| 혼합 영양제 SKU | 생산관리 소유 `supplementTypes` |
| 기타 부자재 | 재고관리 소유 `supplies` |
| 출고 포장박스 | 재고관리 소유 `packingBoxTypes` |

영양제의 개별 구매 원료와 혼합 SKU는 동일 품목이라고 가정하지 않는다. 레시피에는 재고에 연결하지 않은 원료도 있으므로 구매 품목의 포함 범위를 실제 자료로 확인한다. 계란 등 별도 관리 품목도 누락 여부를 확인한다.

원료 가격은 우선 기존 `meatTypes/{id}/priceHistory`를 그대로 참조하는 방식을 권장한다. 통합 화면을 위해 모든 이력을 물리적으로 이동할 필요는 없다. 새 단가 저장 구조를 선택한다면 원본 경로·문서 ID로 재실행 시 중복을 방지하고, 전후 건수와 각 필드 대조가 끝날 때까지 원본을 유지한다.

다른 품목군에는 구매처·규격·구매 단위·포장당 수량·구매금액·환산 단가·적용일·변경자를 관리할 수 있게 설계한다. 예: 드라이아이스 원/kg, 케이블타이 원/봉과 원/개, 스티로폼 박스 규격별 원/개. 부가세와 배송비 포함 기준은 화면에 명시하고 업무 기준을 정해야 한다. 목록 간 동일 품목은 이름으로 자동 병합하지 않는다.

포장박스에는 기존 `unitPriceA`, `unitPriceB` 필드가 있으므로 의미와 사용 경로를 먼저 확인한다. 기존 값을 새 단가와 별개로 중복 관리하지 않는다. 제품 기부 단가(`donationPrices`)는 구매 단가와 용도가 다르므로 합치지 않는다.

## 5. 권한과 앱 간 경계

현재 생산관리 저장소의 `firestore.rules`와 확인한 재고관리 코드에는 `meatTypes` 및 그 `priceHistory`를 생산 앱 사용자만 읽고, 생산 admin/office만 쓸 수 있게 한 규칙이 있다. **운영 배포 규칙 자체를 조회한 결과는 아니다.**

따라서 재고관리에서 목록을 불러오는 것만으로 작업이 끝나지 않는다. 실제 운영 규칙을 확인하고 재고관리의 단가 담당 역할에 필요한 원료 목록 조회·가격 이력 조회·가격 추가 권한을 좁게 허용해야 한다. 생산 역할을 재고 사용자에게 추가해 우회하지 않는다. 원료 부모 문서·재고 수량·레시피 쓰기 권한까지 확대하지 않는다. 신규 가격의 작성자·날짜·금액 검증 및 변경 이력 정책도 함께 정한다. 이전 규칙은 현재 update/delete도 허용하므로 기존 이력이 이미 불변이라는 전제로 설계하지 않는다.

## 6. 생산관리에서 제거한 것과 남긴 것

- `src/pages/settings.js`: 원료 단가 설정 영역·수정 모달·조회/저장 연결 제거. 설정 영역 8개 → 7개. 미리 준비하는 영역도 7개로 변경.
- `src/services/meatPrices.js`: 이전 스키마와 가격 선택 동작을 확인할 참고 코드로 유지. 생산관리 화면에서의 import·호출은 제거했다. 파일이 남아 있어도 자동 실행되는 작업은 아니다.
- `firestore.rules`, 가격 이력 및 감사 로그: 이번 작업에서 변경하지 않음. 보안 규칙상 기존 쓰기 권한을 폐지한 것은 아니며, 구버전 배포 화면의 편집 기능도 배포 전까지 남을 수 있다.
- 생산·레시피·재고 차감 기능은 이번 수정 범위 밖이다. 확인한 생산 입력/통계 코드에는 원료 단가를 이용한 원가 계산 연결이 없다.

## 7. 재고관리 인수 시 확인할 항목

1. 운영 원료별 이력을 읽기 전용으로 조사한다. 비활성 원료·미등록·미래 가격·같은 적용일·잘못된 값도 구분한다. 조사 전후 쓰기는 없어야 한다.
2. 기존 문서 ID·원료 ID·금액·적용일·작성자·Timestamp가 보존되는지 대조한다.
3. 재고관리 전용 계정으로 필요한 목록·가격 조회와 허용 역할의 가격 추가를 검증한다. 비허용 역할은 차단한다.
4. 기준일별 선택, 같은 적용일의 등록시각 우선, 미래 가격 제외, 미등록과 0원 구분을 검증한다.
5. 신규 입력·중복 제출·오류 후 재시도에서도 이력이 덮어써지거나 중복 생성되지 않게 검증한다. 재고 수량·레시피 변경이 없는지 확인한다.
6. 생산관리의 남은 7개 설정 영역이 정상 작동하고 가격 이력을 조회/쓰기 하지 않는지 확인한다.

이 문서는 구현 인수용이며, 재고관리 구현·운영 데이터 백업·이력 이관·운영 권한 변경·양 앱 배포 완료를 의미하지 않는다.
