# 중복입고·취소 수량 검사 — 구현·검증 완료, 운영 미배포

## 변경 범위

- `src/services/receiptIntegrity.js`: 원료·봉투·계란·영양제 입고의 읽기 전용 검사.
  - 같은 입고예정 ID에 복수 입고가 연결되면 수량·날짜가 달라도 확인 후보.
  - 직접 연결이 없으면 같은 품목·단계·단위·수량이 3일 이내 반복된 경우 중복 **의심** 후보. 서로 다른 예정에 명시적으로 연결된 입고는 제외.
  - 취소 원본 존재, 같은 품목/재고, 반대 수량, 취소 식별자, 사유, 전후 재고 산술을 기존 취소 계약으로 검증.
  - 원료 원본 g는 표시에서만 kg로 환산. 다른 단위와 합산하지 않음.
- `src/services/statsAutomation.js`: 검사 후보·컨펌 본문·해결 근거·중복 방지 연결.
  - 취소 불일치로 기존 통계 계산을 할 수 없으면 통계를 임의 복구하지 않고 보류. 독립된 취소 오류 후보는 판단 가능.
  - 확인 보류 품목의 중복입고 판단은 기존처럼 보류.
  - 동일 원본의 기존 수량 컨펌이 있으면 식별자/회차/알림 수준을 유지하고 본문에 추가 근거만 보강. 이후 매일 재검사해도 새 컨펌 없음.
  - 새 종류도 활성화일 이전 기록을 소급 발송하지 않음. 시간 경과·조회 누락·읽음 처리는 해결 증거가 아님.
  - 중복 의심은 연결된 정확한 취소/통계 제외 등 명시적 근거로만 해결. 정상 입고가 여러 번 있었을 수도 있으므로 자동 재고 수정은 하지 않음.
- `src/pages/statsAutomationPreview.js`: 두 새 종류의 날짜·수량·비교 원본·판단 근거 표시.
- `scripts/prepareStatsConfirmBackend.mjs`, `scripts/syncStatsAutomationBackend.mjs`: 신규 검사 모듈의 서버 패키지 누락 방지.

## 검증

- 관련 단위·서버 계약·통계 회귀 테스트 통과. 기존 통계 집계 파일·재고 저장 함수·규칙·설비 주기 변경 없음.
- `npm run build` 및 격리 서버 TypeScript 빌드 통과.
- 실제 Firestore SDK 에뮬레이터: 각 새 종류별 동시 발송 시도 3회 → 테스트 수신자 2명에게 정확히 2문서. 확인·대화 입력 후 재시도 3회 → 신규 0, 확인·대화·본문 동일. 기존 컨펌/재고/원본/설비 문서 동일, 활동·팝업 문서 0.
- 보관된 운영 스냅샷(2026-10-23 14:00 KST 관측): 세 통계 결과 동일, 입력 전체 불변, 재평가 알림 식별자 동일. 과거 계란 300개 반복 2건은 의심 후보이나 활성화일 이전이라 발송 후보 0. 두 건은 오류 확정이나 통계 정정 대상이 아님.
- 증거: `output/receipt-integrity/emulator-result.json`, `output/receipt-integrity/archived-snapshot.json`.

## 적용 상태·한계

운영 DB 쓰기·실제 알림 발송·운영 배포 없음. 서버 패키지는 비활성 환경 설정으로 로컬 빌드만 했다. 기존 운영 알림 설정과 오전 9시 실행은 변경하지 않았다.

연결 근거가 없고 수량도 다르거나 3일을 넘는 반복 입고는 이번 유사 입고 규칙만으로 판정하지 않는다. 원본 연결이 없는 과거 일반 재고 조정도 취소로 임의 해석하지 않는다. 빵판/동결판 내부 이동 및 완제품의 재고앱 전달은 외부 수급 통계 범위 밖이므로 변경하지 않는다.
