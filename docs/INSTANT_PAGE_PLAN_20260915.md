# 생산관리 기본 화면 즉시 전환 실행 계획

작성: 2026-09-15 · 상태: **계획 확정, 새 구현·성능 실험·배포 미실행**

## 1. 결론과 약속의 범위

**유료 요약 서버 없이, 준비된 메뉴의 실제 업무 내용을 클릭 후 0.3초 이내에 표시하는 구조로 개선할 수 있다.** 코드와 데이터를 미리 준비하고, 화면을 떠나도 표시용 결과를 보관하면 클릭할 때 서버 응답을 기다리는 경로를 없앨 수 있기 때문이다. 다만 현재 직원 PC에서 모든 메뉴가 이 목표를 달성한다는 실측 증거는 없다. 이 문서는 먼저 작은 구현 실험으로 가능 여부를 입증하고, 통과한 구조를 전체 메뉴로 확대하는 실행 계획이다.

| 상황 | 목표와 완료 판정 |
| --- | --- |
| 로그인 후 코드·기본 데이터 준비가 끝난 메뉴 | 클릭부터 해당 선택 상태의 실제 행·카드와 조작부 표시까지 **메뉴별 p95 ≤300ms**. 로딩 문구·제목만 표시하는 것은 실패 |
| 재방문 | 다른 메뉴 5개 방문 후, 전체 메뉴 순환 후, 31초·5분·30분 뒤에도 같은 목표. 연결을 끊어도 마지막 서버 확인본은 표시 가능해야 함 |
| 통상 업무 흐름 | 정상 네트워크·인증 완료 상태의 기본 메뉴 전환에서 **미준비 클릭도 포함한 p95 ≤300ms**, 클릭 직전 준비율 ≥95%를 각 메뉴/역할별로 판정. 충족하지 못하면 조건부 재방문 개선만 보고 |
| 최초 로그인·미준비 메뉴 | 별도 측정. 현재 운영판보다 첫 업무 내용 표시가 늦어지면 실패. 첫 접속을 오래 대기시켜 이후 숫자를 좋게 만드는 방식 금지 |
| 새로운 날짜·통계 기간·전체 이력·처음 펼치는 상세 | 해당 key가 준비됐으면 같은 목표. 미준비 상태는 별도 조회시간으로 공개. 무한한 기간·모든 이력을 선조회하지 않음 |
| 최신 데이터 | 마지막 서버 확인 시각과 갱신 상태를 구분. 네트워크 장애 중 최신성·신규 조회 0.3초는 보장할 수 없음 |
| 저사양 검증 | 대표 저사양 PC 또는 4배 CPU 제한에서 준비된 화면 p95 ≤500ms를 보조 목표로 검증 |

여기서 p95는 측정한 방문의 95%가 목표 시간 이내라는 뜻이다. 모든 환경·모든 클릭의 최대 300ms를 뜻하지 않는다. 완전 cold·장애 주입·dirty 이탈 확인에서 사람이 대기한 시간은 표본을 보존하되 별도 기준으로 판정한다. 준비율도 각 메뉴/역할별 분모와 함께 기록하며, 자주 쓰는 메뉴가 느린 메뉴를 가리지 않게 한다. **15개 화면 중 하나라도 미검증이면 ‘전 페이지 완료’로 쓰지 않는다.**

## 4. 구현 구조와 안전 계약

### 4.1 변경할 흐름

1. 인증·권한·한국 날짜 확정 후 현재 메뉴를 최우선으로 연다.
2. 현재 업무 내용이 보인 다음, 허용된 메뉴의 코드와 기본 모델을 여유 시간에 준비한다.
3. 사용자가 메뉴를 누르면 같은 세션·선택 조건의 준비된 모델을 즉시 렌더한다.
4. 별도로 서버 변경을 확인한다. 변경이 없으면 큰 DOM 재생성을 하지 않는다.
5. 편집 중이면 최신 결과를 보류하고 변경 안내를 표시한다. 저장 시에는 화면에 보인 기준과 서버 현재 값을 다시 검증한다.

새 프레임워크, DB/Hosting 이전, 전 메뉴의 숨겨진 DOM 보관, 디스크 데이터 캐시, 주기적인 전 컬렉션 새로고침은 도입하지 않는다. 기존 셸·페이지 이탈·모달·Sortable/Chart 정리 방식을 유지한다.

### 4.2 준비 데이터와 표시 기준을 분리한다 — 다른 작업보다 선행

현재 `withReadCommand()`는 `resource.observations`를 검증 기준으로 복사한다. 배경 조회가 이를 B로 바꾸고 화면 입력은 A를 유지하면, B 검증을 통과한 뒤 A 기준 값을 저장하는 위험이 생긴다. 따라서 다음 세 객체를 구분한다.

| 객체 | 역할 |
| --- | --- |
| `cacheRevision` | 배경에서 완성한 읽기 전용 `model + observations + key + epoch + revisionId` |
| `viewRevision` | 현재 화면에 실제 적용된 동일 묶음. 해당 화면 명령이 참조하는 기준 |
| `pendingRevision` | 입력·포커스·모달·명령 처리로 아직 적용하지 않은 새 묶음 |

모델과 observations는 한 번에 교체한다. 활성 명령은 시작 시점의 viewRevision을 고정한다. 준비 성공·재연결·일반 새로고침이 `busy/blocked/pending command`를 해제하면 안 된다. 캐시가 최신이라는 이유로 서버 읽기, 마감 확인, 토큰 역할 확인, 단일 실행 보호를 생략하지 않는다.

기존 다단계 쓰기를 이번 작업에서 새 transaction으로 바꾸지 않는다. 현재 보호의 한계도 숨기지 않는다. 표시 속도 개선을 이유로 재고·outbox·영양제 차감·FIFO·회차·batchNo·환산표 규칙을 바꾸지 않는다.

### 4.3 API와 key

`pageResources.js`를 작은 단계로 확장한다. API 이름은 아래를 기준으로 구현한다.

```js
resource.prepare(key, loader, { priority, epoch }); // 캐시만 생성, 같은 key의 요청 합침
resource.activate(context, key, { onChange });     // viewRevision 설치/반환
resource.releaseView(context);                   // DOM 연결만 해제
resource.getCommandBaseline(context);            // 실제 표시 기준 반환
```

- loader는 `scope`와 명시적인 params를 받고 DTO를 반환한다. DOM, currentMenu, 모듈 전역 선택값 변경, cleanup 등록, 업무 쓰기를 수행하지 않는다.
- key는 UID·역할·KST 날짜·epoch·route·선택 날짜/탭/기간/집계/필터·모델 schema를 포함한다. `freezeOp`는 동결판 부모 화면과 하위 탭 소유권도 구분한다.
- 준비 중 클릭하면 기존 Promise를 사용하고 foreground 우선순위로 올린다. 화면 요청을 중복 시작하지 않는다.
- prepare 완료는 epoch·요청 key·요청 generation을 확인한다. activate/DOM 적용에는 view context 검사도 추가한다. 정상 메뉴 이탈만으로 유효한 배경 결과를 버리지 않으며, 로그아웃·권한 변경·자정 이후 응답은 폐기한다.
- 취소는 대기열/결과 적용을 중단한다는 뜻이다. 이미 시작한 Firestore 요청까지 반드시 네트워크 취소된다고 가정하지 않는다.
- query 공유는 기존 SDK `queryEqual`과 doc path를 사용한다. collection 이름만 같다는 이유로 정렬·필터가 다른 결과를 합치지 않는다.

### 4.4 모델 보관과 메모리

- 14메뉴 + 동결가동의 **기본 선택 상태 모델**을 세션 동안 보관 대상으로 둔다. 실제 재방문 선택 상태를 기존 동작대로 유지하고 그 key를 사용한다.
- 임의 날짜·검색·추가 통계 기간·상세 원본은 별도 LRU로 제한한다. 3개 제한을 무작정 15개로 바꾸는 작업으로 끝내지 않는다.
- listener 해제 시 모델은 `stale`로 전환한다. 같은 세션의 마지막 서버 확인본으로 즉시 표시하고 재연결한다.
- 최초 cache-only 빈 snapshot을 서버 확인된 빈 목록으로 승격하지 않는다. permission-denied 시 해당 이전 데이터도 지운다.
- 공용 master는 중복 보관을 줄인다. 초기 모델 예산은 기존 **64MiB를 soft budget**으로 유지하되 모델·observations·공유 원본·복사본을 합산한다.
- SDK snapshot, 페이지 전역 배열, DOM, Chart는 브라우저 heap으로 별도 측정한다. 64MiB를 탭 전체 메모리 상한으로 표현하지 않는다.
- 초기에는 방어 복사를 유지한다. 실제 느린 메뉴에서만 in-place sort/edit를 점검한 후 읽기 전용 DTO와 편집 대상 복사로 바꾼다.
- 예산 초과 시 상세 모델부터 축소/퇴거한다. 기본 모델까지 퇴거하면 준비 완료 표시와 측정 분모에 반영한다. 전체 준비가 된 것으로 보고하지 않는다.

### 4.5 준비 작업 순서와 읽기 예산

- 우선순위: 저장 검증/실제 메뉴 진입 → pointer/focus로 사용 의도가 확인된 메뉴 → 이미 받은 원본의 모델 계산 → 추측 데이터 조회.
- 배경 네트워크는 **실제 SDK read 단위 동시 1개**부터 시작한다. loader 하나가 내부 Promise.all로 여러 조회를 무제한 시작하지 못하도록 read scope에서 제한한다. 지연·읽기량 기준을 통과한 경우에만 2개로 조정한다.
- foreground 요청은 배경 대기열 앞에 둔다. 이미 진행 중인 배경 요청의 합류 또는 결과 폐기로 처리한다.
- hidden/offline/절전 복귀 직후 세션 확인 전/Save-Data/저장 처리 중에는 새 추측 조회를 중단한다. 빠른 네트워크가 확인되지 않으면 보수적으로 동작한다.
- 메인·생산·공용 master, 원료·계란·봉투·영양제, 동결 계열·입고예정·설비, 통계·설정 상세 순서를 시작값으로 사용한다. 실제 역할별 업무 시퀀스 결과로 확정한다.
- 통계 전체 기간, 가격 history 전체, 전 메뉴의 과거 로그를 접속 즉시 모두 조회하지 않는다. 실패한 메뉴 준비가 현재 본문을 지우거나 전체 큐를 멈추지 않게 한다.
- `prepare()` 중 업무 write는 0회여야 한다. 특히 메인의 자동 알림 작성은 실제 메인 방문 시 기존 coordinator가 실행하고, 완료 전 마감 차단을 유지한다.

**새 서버 0개와 Firestore 추가 과금 0원은 다르다.** 방문하지 않을 메뉴를 미리 읽으면 기존 DB 사용량이 증가할 수 있다. 기본 정책은 공용 데이터 재사용과 재조회 감소를 먼저 확보하고 그 절감 범위에서 준비한다. 단일 메뉴만 쓰고 종료하는 경우도 비용 비교에 포함한다. 읽기 증가가 확인되면 추측 선조회를 줄이고, 그 결과 준비율이 떨어지면 전 메뉴 즉시 목표를 미달로 보고한다. 두 목표를 모두 달성했다고 가정하지 않는다.

### 5.1 하위 화면별 완료 행

각 행에 `cold / prepared / stale / 내용 동등성 / reads / heap / 결과 증거 경로`를 기록한다. 탭별 화면 key를 혼합해 평균내지 않는다.

| 묶음 | 개별 검증 대상 |
| --- | --- |
| 원료 4개 | 냉동창고, 전처리, 재포장, 채소/과일 |
| 동결판 3개 | 빵판, 동결판, 동결가동(`freezeOp`) |
| 통계 6개 | 생산량, 원료 소모량, 봉투 소모량, 계란 사용량, 일별 생산 현황, 영양제 |
| 설정 8개 | 담당자 관리, 메뉴별 담당자 그룹, 마감 차단/경고 설정, 공휴일 관리, 생산지시서 카테고리 순서, 원료 명칭 통합, 시스템 설정값, 원료 단가 관리 |
| 상세/기간 | 생산 날짜 변경, 계란 FIFO 펼치기, 봉투/동결제품/설비 상세, 입고예정 완료 펼치기, 통계 임의 기간과 Excel |

설정 8개·통계 6개가 준비되지 않았는데 상위 메뉴 제목이 빨랐다는 이유로 전체 완료 처리하지 않는다. 모든 기본 메뉴 준비 목표와 하위 상세 준비 목표의 달성률을 따로 보고한다.

### 5.2 조회 축소 전 확인 절차

1. 해당 문서 필드의 missing/null/status/동률 timestamp/삭제 기록을 포함한 fixture를 만든다. 운영 데이터 분포는 필요한 범위만 읽기 전용으로 확인한다.
2. 기존 로더와 후보 로더의 ID·정렬·필터·수량·합계·경고를 대조한다. 0건은 서버 확인된 경우만 정상 빈 목록이다.
3. 조건/정렬 변경에 필요한 index와 현재 rules 허용 범위를 확인한다. index 추가가 필요한 최적화는 별도 변경으로 분리한다. 이번 프런트 배포에 규칙 변경을 섞지 않는다.
4. 계산용 전체 범위와 표시용 페이지 범위를 구분한다. pagination은 정확한 계산 원본을 대신하지 않는다.
5. 쿼리 의미나 UI 동등성을 확보하지 못하면 기존 조회를 유지하고 준비/보관/렌더 개선만 적용한다. 그 상태로 성능 목표가 실패하면 실패로 기록한다.

### 6.1 새 경로 활성화와 파일 경계

- 기존 `VITE_PRODUCTION_VIEW_MODE=session`을 유지한다. 별도 `VITE_INSTANT_PAGE_ROUTES` 목록을 `src/config/performanceFlags.js`에 추가하고 기본값은 빈 목록으로 둔다.
- `scripts/readpathRelease.mjs`의 flags 검증, `readpath.release.json`, release manifest, 관련 테스트를 함께 확장한다. 과거 4개 필드 manifest는 새 필드 빈 값으로 해석하고, 새 prepare는 명시적으로 기록한다. 알 수 없는 key/route·중복 route는 계속 차단한다.
- `src/state/pagePreparation.js`는 큐가 실제로 필요해진 3단계에 신설한다. `src/router.js` 또는 작은 `src/pageModules.js` 한 곳에서 import loader를 공유한다. 모듈 최상위 부작용을 점검하고 render를 호출하지 않는다.
- 새 구조 활성 route만 준비 큐와 새 view 계약을 사용한다. 비활성 route의 현재 동작은 유지한다. readCommand가 새 baseline handle을 받는 경로와 기존 경로를 명시적으로 구분한다.
- listenerPool·공용 queue 등 공유 기반 변경도 flag가 빈 목록일 때 기존 의미를 유지해야 한다. **flag-empty 상태의 기준판 대비 내용·수명·저장 동등성**을 검증하고, 특정 route ON/OFF만 확인하는 것으로 롤백 가능 판정을 대신하지 않는다.
- 메뉴 순수 로더는 우선 기존 page 파일에서 추출한다. 크기·독립 검증에 도움이 되는 경우에만 `src/pages/models/`로 이동한다. 전 페이지 재작성은 하지 않는다.
- 렌더가 목표 초과일 때만 첫 viewport와 다음 화면분부터 순차 렌더를 적용한다. 합계는 전체 정확한 원본으로 계산한다. 가상 목록 도입은 sticky header/그룹/스크롤/찾기/인쇄/내보내기 보존 증거가 있을 때 별도 커밋한다.

## 7. 계측과 인수 시험

### 7.1 기록할 지표

- navigation ID, session epoch, role, route와 비식별 params, 코드/모델 준비 여부(클릭 직전 고정), model revision·age·completeness.
- `appEntry`, `authReady`, `navigationRequested`, `codeReady`, `cacheContentPaint`, `serverObserved`, `freshContentPaint`, `interactive`, 실패/취소/timeout.
- 기준 시작은 실제 클릭 handler 진입. dirty 이탈 확인에서 사용자가 머문 시간은 별도 필드로 남기되 전체 지연도 보관한다.
- 완료는 해당 route/key의 올바른 업무 행/카드·조작 handler·차트 데이터 첫 프레임이다. 원료의 미완료 async와 설정의 접힌 제목을 완료로 인정하지 않는다.
- background/foreground/command마다 query 시작·공유·초기 server snapshot·후속 변경·재연결·전달 문서 수·사용/폐기된 준비 결과를 기록한다.
- 네트워크 bytes는 실제 브라우저 관측값을 사용한다. DTO JSON 크기를 전송량이라고 쓰지 않는다. 문서 전달 수 역시 정확한 과금 건수와 구분한다. 공유 프로젝트의 운영 사용량은 다른 앱 트래픽 영향을 함께 표시한다.
- diagnostic/export는 개발·검증 모드의 명시적 도구로 제공한다. 직원 화면 기본 노출과 개인정보·문서 내용 저장은 피한다. UI 검증 도구의 허용 범위 안에서 JSON을 내보내고 검증한다.

### 7.2 실험 매트릭스

| 축 | 실행 내용 |
| --- | --- |
| 비교 | 현재 운영 source 고정, 같은 fixture/브라우저/기기/역할. 기준판·후보판 순서를 교대 |
| 표본 | 자동 브라우저에서 메뉴/조건별 최소 50표본, p50/p95/max·실패율. 실제 직원 PC는 역할/핵심 화면별 최소 30표본 |
| 방문 | 완전 cold, 로그인 후 미방문, 코드만 준비, 코드+모델 준비, 다른 메뉴 5개 후 복귀, 전체 1·2바퀴, 31초/5분/30분 복귀 |
| 업무 흐름 | 실제 직원의 일반 시퀀스, 단일 메뉴 사용 후 종료, 빠른 A→B→A, 100회 전체 메뉴 순환. 준비 대기시간·준비율 포함 |
| 기기/역할 | 불만 신고 PC 포함 직원 PC 최소 2대, admin/office/production의 실제 허용 화면. 새 권한 부여·계정 사칭 없이 검증 |
| 장애 | 50/150ms 외 800ms·2초 tail, query 1개 10초 정지, offline/timeout/permission-denied, 느린 CPU |
| 최신성 | 다른 client create/update/delete, 정렬·합계 변경, metadata-only event, 입력/모달 중 새 revision, 재연결 |
| 세션 | 로그아웃→다른 사용자, 역할 축소, 자정·절전 복귀, 준비 중 날짜 변경, 이전 응답 역순 도착 |
| 쓰기 회귀 | emulator에서 A화면/B서버 충돌, 마감·권한 변경, 더블클릭, pending timeout·ACK 손실, 재전송 금지, FIFO/환산/차감 동등성 |

운영 검증은 필요한 읽기와 화면 확인으로 제한한다. 메인 진입은 기존 자동 알림 부작용이 있을 수 있으므로 단순 ‘조회 전용’이라고 가정하지 않는다. 성능 자동 반복은 순수 로더와 fixture/emulator에서 실행하고, 운영 기기의 정상 메인 방문으로 생긴 기존 동작은 별도 기록한다. 테스트 저장·삭제·재고 변경을 운영에서 수행하지 않는다.

### 7.3 출시 기준

1. 1절 시간 기준을 정상 네트워크·인증 완료의 기본 메뉴 전환에서 **각 메뉴/역할별** 통과. 준비율의 분모에 미준비 클릭을 포함한다. 최초 업무 시간은 기준판 대비 악화 없음. cold·장애·사용자 확인 대기는 별도 판정하되 실패와 timeout을 결과에서 숨기지 않음.
2. 첫 화면의 품목·카테고리·수량·합계·정렬·경고와 전체 이력/추출 결과 동등성 통과. 잘못된 빈 목록·다른 날짜/탭 값 표시 0건.
3. 입력값·포커스·모달·명령 기준 revision 보호, 준비만으로 업무 write 0건. 권한 없는 데이터 노출 0건.
4. 동일 업무 시나리오의 서버 문서 전달/재연결 및 Firestore 데이터 전송 bytes가 기준판을 초과하지 않음을 기본 예산으로 적용. 코드 선조회 bytes는 별도로 비교하고 첫 업무 표시를 지연시키지 않아야 한다. 비용을 직접 관측하지 못하면 ‘과금 무증가 확정’으로 쓰지 않음.
5. 초기 20회 순환 후 안정점과 100회 후 정리 가능한 잔류 heap 비교: 증가 ≤10%를 초기 기준으로 사용. 지속 증가·listener/Chart 누수 0. 실제 기기 절대 메모리 예산은 0단계에 기록해 고정하고 결과를 본 뒤 임의 완화하지 않음.
6. 외부 변경은 활성 화면에서 기준판보다 늦게 반영되지 않아야 한다. draft로 적용을 보류하면 안내 도착 시간을 측정한다. 전체 재렌더로 입력을 덮지 않음.
7. unit/integration/build/release 검증, flag-empty 상태의 기존 경로 동등성, 실제 열린 구버전 탭의 전 메뉴 확인. 단순 테스트 개수로 대체하지 않음.

## 8. 실행 명령과 산출물

이 절은 **향후 구현 실행용**이다. 이번 계획 작성에서는 실행·배포하지 않았다. 기존 `package.json`에 실제 있는 명령을 기준으로 한다.

```powershell
Set-Location C:\dev\fant-production
git status --short
git rev-parse HEAD
git remote -v
npm run test:readpath
npm run build
git diff --check
```

새 테스트는 구현 파일을 흉내 내는 검증보다 7절 사용자 흐름·경합·데이터 동등성을 우선한다. 새 파일을 추가하면 `test:readpath` 목록에 포함한다. 현 `perf:menus`와 `perf:measure`는 보조 회귀로 유지한다. 실제 브라우저 측정용 runner와 fixture replay를 0단계에서 추가하고 정확한 실행법을 산출물 README에 기록한다.

통합 테스트는 `scripts/runReadpathEmulator.mjs`를 읽고 rules 정본 HEAD·localhost emulator 설정을 확인한 뒤 실행한다. 프로젝트는 `demo-fant-readpath`, Firestore는 localhost:8088이다. 정본 경로가 다르면 `INVENTORY_RULES_REPO`를 정확한 체크아웃에 설정한다. production 자격증명으로 테스트를 우회하지 않는다.

```powershell
npm run test:readpath:integration
```

산출물은 `output/instant-page/`에 작업별 보관한다: `baseline/`, `candidate/`, `parity/`, `browser/`, `memory/`, `reads/`, `release/`. 각 폴더에 source·flags·fixture hash·시각·기기/역할·조건·실패 포함 표본 수를 남긴다. 개인정보가 든 운영 원본은 커밋하지 않는다. 최종 `docs/INSTANT_PAGE_ACCEPTANCE_20260915.md`에는 전 메뉴/하위 화면별 비교와 미달 항목을 기록한다.

## 9. 배포와 복구

1. 새 route flag는 로컬/검증 환경에서 비활성→시험 메뉴→전체 순서로 검증한다. GitHub Pages는 빌드 단위이므로 route 범위는 release flags로 고정한다. 존재하지 않는 원격 사용자별 rollout 기능을 가정하지 않는다.
2. 모든 변경·검증 문서를 검토하고 필요한 파일만 커밋한다. release 스크립트가 source clean을 요구하므로 `output/` 외 미커밋 변경을 둔 채 우회하지 않는다.
3. `readpath.release.json`의 viewMode=session, 허용 route 목록, 새 활성 목록을 확인한다. 현재 assets 보존 manifest를 유지한다.
4. 아래 명령으로 검증한 동일 산출물을 배포한다. gh-pages가 준비 이후 바뀌면 다시 prepare한다. 임의 `gh-pages -d dist`로 검증을 우회하지 않는다.

```powershell
npm run release:prepare
node scripts/deployReadpathRelease.mjs --verify-only
npm run deploy
npm run verify:readpath-release
```

5. Pages 실행 성공과 live release source/flags/모든 asset hash를 확인한다. 앞 배포에서 열린 탭을 유지한 채 미방문 메뉴를 모두 연다. 자동 reload 0, 실제 본문 확인 후 신규 탭도 확인한다.
6. 실패하면 새 활성 목록을 빈 값으로 되돌린 **새 커밋/새 배포**로 현재 session 경로에 복귀한다. 공유 기반 수정 자체의 장애로 flag OFF가 충분하지 않으면 해당 구현 커밋을 검토해 revert하고 기존 경로를 복구한다. 두 경우 모두 현재의 asset 보존기를 유지한 채 새 manifest를 만든다. gh-pages를 과거 tree로 강제 되돌리거나 이전 chunks를 삭제하지 않는다.
7. 기존에 열린 후보판 탭은 새 배포만으로 즉시 코드가 바뀌지 않는다. 복구가 필요한 직원에게 입력 보존 후 명시적 새로고침을 안내한다. 자동 강제 새로고침은 하지 않는다.
8. 서버 요약은 복구 수단으로 켜지 않는다. 정상화 여부는 실패했던 동일 화면·기기·방문 조건으로 다시 판정한다.

## 10. 검토 중 발견한 별도 정상동작 결함

`src/pages/frozenPan.js` 발주 삭제 handler의 `if (targetRow && await blockIfClosed(targetRow.date), command) return;`는 콤마 연산자로 최종 `command` 객체를 조건으로 평가해 조기 종료한다. 이번 계획에서는 코드를 수정하지 않았다.

향후 구현의 사전 기능 기준에 **미마감 발주 삭제 성공 / 마감일 차단 / 취소 확인 시 무변경** fixture를 추가하고 별도 작은 버그 수정 커밋으로 처리한다. 운영 실제 발주를 삭제해 재현하지 않는다. 이 결함을 로딩 개선의 성과로 합산하지 않는다.

## 11. 실행 체크리스트

- [ ] 현재 source·운영 flags·서버 OFF·자산 보존 상태 재확인
- [ ] 0단계: 14개 메뉴와 모든 하위 화면의 실제 내용 기준·기기별 baseline 기록
- [ ] 1단계: prepare/activate와 cache/view/pending 분리, 저장 기준 회귀 통과
- [ ] 2단계: 생산·원료·통계·설정 내용의 작은 실험으로 목표 입증
- [ ] 3단계: 준비 큐·공유 원본·읽기/메모리 예산 통과
- [ ] 4단계: 나머지 전체 행 구현 및 계산/표시 동등성 통과
- [ ] 5단계: 직원 PC·장시간·외부 변경·오류·입력 보호 인수
- [ ] 배포 전 구버전 탭 준비, 테스트/build/hash 검증 후 순차 배포
- [ ] 실제 운영 source와 구버전/신규 탭의 전 메뉴 본문 확인
- [ ] 메뉴별 수치·읽기량·메모리·준비율·한계를 인수 문서에 기록

**현재 체크 완료 항목은 없다.** 이번에 완료한 것은 코드 근거를 확인한 실행 계획이다. 2단계 실험을 통과하기 전에는 ‘모든 페이지 0.3초가 확실하다’고 단정하지 않는다.
