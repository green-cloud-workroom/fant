# 배포 후 메뉴 로딩 실패 복구

2026-09-15 직원의 생산관리 지연·내용 로딩 실패 신고를 확인했다. 실제 열려 있던 사무실 계정의 생산 입력 화면에서 오류와 브라우저 로그를 확인했다.

## 확인한 원인

오류 탭은 이전 `index-BN9Hd0zI.js`(source8df0d70)를 실행 중이었다. 이 파일이 나중에 요청한 `production-DzHW_yOy.js`, `meat-CptlvwxP.js`가 후속 배포에서 삭제돼 `Failed to fetch dynamically imported module`이 발생했다. 기존 배포는 dist를 새로 만들고 gh-pages의 파일 목록을 교체했으며, 이미 열린 탭이 사용하는 이전 lazy chunk를 보존하지 않았다. 새로고침 후 현재 생산 목록이 정상 표시되는 것을 확인했다.

이 증상은 확인된 배포 결함이다. 모든 운영 지연이 이 원인 때문이라고 단정하지 않는다. 합성 조회 측정/새 탭 확인만으로 장시간 열린 직원 탭의 배포 호환성을 검증하지 못했다.

## 수정

- release 준비 시 gh-pages의 현재 파일과 최근7개 배포의 assets를 수집한다. 이번에는 이미 삭제된 이전 파일까지 복원한다. 이후 현재 배포가 보유한 이전 assets가 다음 배포에도 이어지므로 열린 탭의 파일을 자동 삭제하지 않는다.
- 보존 경로는 assets 하위 파일만 허용하고, 동일 경로의 내용 변경은 배포를 차단한다. index.html/release.json은 현재 빌드만 사용한다. 총100MiB 초과는 자동 삭제 대신 검토를 요구한다.
- 준비한 git blob 목록을 manifest에 고정하고 재빌드 때 동일하게 복원한다. 준비 이후 다른 배포가 있으면 전송을 중단한다. 이전 파일도 운영 HTTP/hash 검사에 포함한다.
- 모듈 로딩 실패 시 같은 실패한 import를 반복하지 않고 명시적 앱 새로고침 버튼을 제공한다. 자동 새로고침으로 입력을 지우지 않는다. 일반 데이터 오류의 화면 내 재시도는 유지한다.
- 서버 요약 off와 전용 함수 삭제 상태는 유지한다. 업무 계산·재고 쓰기·권한·원본 데이터는 변경하지 않았다.
